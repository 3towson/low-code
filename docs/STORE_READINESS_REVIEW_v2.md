## N1 ❌ หน้าเว็บที่บอกว่า "สำเร็จ" ทั้งที่ไม่ได้ทำงาน

### `app/web/reset-password.html`
`window.SUPABASE_URL` และ `window.SUPABASE_ANON_KEY` ไม่มีการกำหนดค่าที่ไหนเลย บล็อกที่เรียก `updateUser` จึงไม่ทำงาน แต่หน้าเว็บยังแสดง **"เปลี่ยนรหัสผ่านสำเร็จ!"** ผลคือผู้ใช้ (และ reviewer) จะเข้าใจว่าเปลี่ยนรหัสแล้ว ทั้งที่ยังไม่ได้เปลี่ยน

แก้:
- ใส่ URL กับ anon key ของ Supabase ลงในหน้า (เป็นค่าสาธารณะอยู่แล้ว)
- รองรับลิงก์ทั้งสองแบบ: แบบ PKCE (`?code=` → `exchangeCodeForSession`) และแบบ implicit (`#access_token&type=recovery`)
- ถ้าไม่มี token หรือ client ให้แสดง error ห้ามแสดงหน้าสำเร็จ
- pin เวอร์ชัน `@supabase/supabase-js@2.x.y` ให้แน่นอน
- ทดสอบจริงตั้งแต่ขอรีเซ็ตจากแอป จนถึง login ด้วยรหัสใหม่

### `app/web/dispute.html`
ฟอร์มไม่ได้ส่งข้อมูลไปไหนเลย สร้างเลข ticket ด้วย `Math.random()` แล้วแสดงว่ายื่นคำร้องสำเร็จ แต่นโยบายความเป็นส่วนตัวสัญญาว่า "ดำเนินการภายใน 3 วันทำการ" คนที่ใช้สิทธิ์โต้แย้งตาม PDPA จะคิดว่ายื่นเรื่องไปแล้ว ทั้งที่ไม่มีใครได้รับ

**[ต้องตัดสินใจ]**

| ตัวเลือก | รายละเอียด |
|---|---|
| **A (แนะนำ ทำได้เร็ว)** | เปลี่ยนเป็นหน้าคำแนะนำ + ปุ่ม `mailto:` ที่เติมหัวข้อและเนื้อหาให้ (เบอร์, ประเภทข้อโต้แย้ง, ช่องทางติดต่อกลับ) ไม่สร้าง ticket ปลอม |
| B | สร้าง Edge Function `submit-dispute` + ตาราง `customer_disputes` ตามแผน Dispute Portal ที่แก้แล้ว (OTP, ticket ที่เดาไม่ได้ ฯลฯ) ใช้เวลามากกว่า |

### Deep link `codcheck://login`
`email-verified.html` และ `reset-password.html` ใช้ปุ่ม `codcheck://login` และ `email-verified.html` ยังเปลี่ยนหน้าไปที่ลิงก์นี้อัตโนมัติ แต่แอป**ไม่ได้ลงทะเบียน URL scheme นี้** (ไม่มี `CFBundleURLSchemes` ใน Info.plist และไม่มี `intent-filter` ใน AndroidManifest) บนมือถือจึงจะขึ้น error

แก้: เลือกทางใดทางหนึ่ง
- ลงทะเบียน scheme ทั้งสองฝั่ง หรือ
- เอาปุ่มกับการเปลี่ยนหน้าอัตโนมัติออก แล้วเขียนว่า "กลับไปเปิดแอปแล้ว login" (แนะนำสำหรับเวอร์ชันแรก)

## N2 🔴 Rate limit ยังหลบได้ เพราะเชื่อ header `X-Forwarded-For` ตัวแรก

ไฟล์: `supabase/functions/check-customer/index.ts` → `getClientIp`

ตอนนี้โค้ดอ่าน IP ตัว**แรก**ใน `X-Forwarded-For` ซึ่งฝั่ง client กำหนดเองได้ ถ้าใส่ค่าสุ่มมาทุกครั้ง แต่ละคำขอจะได้ key ใหม่ guest จึงไม่โดนจำกัดเลย (กลับไปเป็นปัญหาเดิมของ P0-6)

แก้:
1. ทดสอบจริงด้วย `curl -H "X-Forwarded-For: 1.2.3.4"` แล้วดู header ที่ function ได้รับ ว่า proxy ของ Supabase เติม IP จริงไว้ตำแหน่งไหน
2. ใช้ header ที่ฝั่ง platform เป็นคนกำหนดเท่านั้น (โดยทั่วไปคือ IP ตัว**สุดท้าย**ใน XFF ที่ proxy เติม หรือ header เฉพาะของ platform) ห้ามใช้ตัวแรก
3. เพิ่มเพดานรวมของ guest ทั้งระบบ เช่น `guest:global:text:day` สำหรับการเรียก Gemini เพื่อจำกัดค่าใช้จ่ายสูงสุดต่อวันได้แน่นอน
4. **[ต้องตัดสินใจ]** เมื่อ RPC rate limit error ตอนนี้ปล่อยผ่าน (fail-open) สำหรับ guest แนะนำให้เปลี่ยนเป็นปฏิเสธ (fail-closed)

## N3 🔴 ผู้ใช้ทั่วไปเรียก `hit_rate_limit` ได้เอง

ไฟล์: `20261013000005_p0_6_postgres_rate_limiting.sql`

`grant execute ... to authenticated` ทำให้ร้านค้าคนไหนก็เรียก `rpc('hit_rate_limit', {p_key: 'user:<uid ของคนอื่น>:day', ...})` ซ้ำๆ เพื่อเพิ่มตัวนับของคนอื่นได้ ผลคือล็อกไม่ให้ร้านอื่นหรือ guest ทั้ง IP ใช้งาน

แก้ด้วย migration ใหม่:
```sql
revoke execute on function public.hit_rate_limit(text, int, int) from authenticated;
```
ให้เหลือแค่ `service_role` เพราะ Edge Function เรียกด้วย service role อยู่แล้ว

## N4 🟠 นโยบายความเป็นส่วนตัวมีข้อความที่ไม่ตรงกับความจริง

ไฟล์: `app/web/privacy-policy.html` (และต้องแก้ให้ตรงกับ `docs/STORE_PRIVACY_DATA_SAFETY.md`)

1. **"ไม่จัดเก็บชื่อจริงของลูกค้าปลายทาง"** ไม่จริงทั้งหมด
   - แถวเก่าใน `cod_reports.customer_name` ยังมีชื่ออยู่ (ดู N5)
   - ภาพหลักฐาน (แคปแชท/ออเดอร์) มักมีชื่อ ที่อยู่ และเบอร์ของลูกค้า
   - ต้องเขียนตามจริงว่า "ภาพหลักฐานอาจมีข้อมูลลูกค้า เก็บใน private storage ให้แอดมินตรวจเท่านั้น และเก็บไว้นาน X"
2. **"ไม่ถูกนำไปใช้ฝึกโมเดล AI ของ Google"** จริงเฉพาะเมื่อใช้ Gemini แบบเสียเงินหรือ Vertex AI ถ้าใช้ Gemini API แบบฟรี (AI Studio) Google อาจนำข้อมูลไปใช้ปรับปรุงบริการ **[ต้องตัดสินใจ]** ตรวจ billing ของ API key ที่ใช้อยู่ แล้วเขียนให้ตรง
3. **"AI สกัดเฉพาะหมายเลขโทรศัพท์"** จริงๆ สกัดชื่อด้วย
4. **ไม่มีตัวตนของผู้ควบคุมข้อมูล:** PDPA กำหนดให้ต้องระบุผู้ควบคุมข้อมูล (ชื่อบุคคลหรือนิติบุคคล + ช่องทางติดต่อ) "COD Customer Check Support Team" ใช้แทนไม่ได้
5. **ไม่ได้ระบุว่าส่งข้อมูลไปต่างประเทศ:** Supabase (ระบุ region) และ Google ประมวลผลข้อมูลนอกประเทศไทย
6. **ไม่ได้ระบุฐานทางกฎหมาย** ในการประมวลผลข้อมูลของลูกค้าปลายทาง ซึ่งไม่ได้ให้ความยินยอม (เช่น ประโยชน์โดยชอบด้วยกฎหมาย)
7. **ระยะเวลาเก็บภาพหลักฐานและรายงาน** ยังไม่ชัด เช่นจะลบรายงานที่เกิน 12 เดือนจริงไหม
8. **"ดำเนินการภายใน 3 วันทำการ"** ผูกกับช่องทางที่ใช้งานไม่ได้ (N1)

> แนะนำให้นักกฎหมายตรวจนโยบายก่อนเผยแพร่จริง เพราะแอปประมวลผลข้อมูลของบุคคลที่ไม่ได้ให้ความยินยอม

### โดเมน `codcheck.app`
อีเมล support, dispute, privacy และบัญชี reviewer ทั้งหมดใช้ `@codcheck.app` และ Bundle ID เป็น `com.codcheck.app` แต่โดเมนนี้มีเว็บไซต์ของใครบางคนอยู่แล้ว **[ต้องตัดสินใจ / ต้องตรวจ]** เจ้าของ repo เป็นเจ้าของโดเมนนี้จริงไหม และอีเมลรับได้จริงไหม
- ถ้าไม่ใช่ ทั้ง reviewer และลูกค้าจะติดต่อไม่ได้ (Apple 1.2 กำหนดให้ต้องมีช่องทางติดต่อที่ใช้ได้จริง) และอาจมีปัญหาเรื่องแบรนด์
- ต้องเปลี่ยนเป็นโดเมนหรืออีเมลที่ใช้ได้จริง

## N6 🟡 การลบบัญชี

- **ลำดับการลบ:** ตอนนี้ลบไฟล์ใน storage ก่อนลบผู้ใช้ ถ้าลบผู้ใช้ไม่สำเร็จ ไฟล์จะหายไปแล้วแต่บัญชียังอยู่ ให้ลบผู้ใช้ก่อนแล้วค่อยลบไฟล์ หรือ retry
- **รายงานที่ยังรออนุมัติ:** หลังลบบัญชี รายงาน `pending` จะไม่มีภาพหลักฐานแล้ว แอดมินตรวจไม่ได้ ให้ Edge Function เปลี่ยนรายงาน `pending` ของผู้ใช้นั้นเป็น `rejected` (เหตุผล "ผู้รายงานลบบัญชี") ก่อนลบ
- **error message:** `ลบบัญชีไม่สำเร็จ: ${deleteError.message}` ส่ง error ดิบกลับไปหาผู้ใช้ ให้เปลี่ยนเป็นข้อความทั่วไป
- **ข้อจำกัดของ list:** `list(prefix, { limit: 1000 })` ลบได้แค่ 1,000 ไฟล์แรก ให้วนลบจนหมด

## N7 🟡 สถานะ `suspended` ไม่ครบในแอป

- `MerchantKycStatus` ไม่มีค่า `suspended` `fromValue` จึงแปลงเป็น `unverified` ร้านที่ถูกระงับจะเห็น dialog "ยืนยันตัวตนร้านค้า" กรอกแบบฟอร์ม แล้วโดน error `MERCHANT_SUSPENDED`
  - แก้: เพิ่ม enum `suspended` + dialog แจ้งว่าถูกระงับ พร้อมช่องทางติดต่อ
- `admin_suspend_merchant` ไม่ได้จัดการรายงานที่ร้านนั้นส่งไว้แล้ว **[ต้องตัดสินใจ]** ตอนระงับร้าน จะเปลี่ยนรายงาน `pending` ทั้งหมดของร้านเป็น `rejected` ไหม และรายงาน `active` เดิมจะยังนับต่อหรือไม่ (แนะนำให้มีตัวเลือกให้แอดมินติ๊กเลือก)
- ยังไม่มีฟังก์ชันยกเลิกการระงับ (`admin_unsuspend_merchant`)
